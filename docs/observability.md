# Logging and observability

## Project scope

Surinort-AST is a Python 3.11+ library, a Typer command-line tool, and a small
stdio Language Server Protocol process. Its main work is parsing and analyzing
local IDS rule files. It has no application database, HTTP server, user
authentication, scheduler, or message broker. Engine verification launches a
local subprocess; parallel parsing uses Python worker processes.

The library uses Python's standard `logging` package. Importing the library
does not configure the root logger or write to stdout. CLI and LSP entry points
configure the `surinort_ast` logger to write to stderr. The CLI also accepts
`--log-level` and `--log-format`, or the `SURINORT_LOG_LEVEL` and
`SURINORT_LOG_FORMAT` environment variables. `SURINORT_ENVIRONMENT`, when set,
is included in JSON events.

```console
surinort --log-level INFO --log-format json parse rules/local.rules
SURINORT_LOG_LEVEL=DEBUG SURINORT_LOG_FORMAT=json surinort validate rules/*.rules
```

A real CLI parse emits a completion summary like this (the sample input rule is
omitted from logs):

```json
{"timestamp":"2026-11-06T21:19:06.885Z","level":"INFO","message":"cli_operation_completed","service":"surinort-ast","component":"cli.shared","event_name":"cli_operation_completed","operation":"cli.parse","duration_ms":27.63,"outcome":"success"}
```

The default level is `WARNING`; normal parsing does not emit per-rule events.
Supported levels are `TRACE` (level 5), `DEBUG`, `INFO`, `WARNING`, `ERROR`,
and `CRITICAL`. The default format is human-readable text. Both formats carry
normalized fields such as `service`, `component`, `event_name`, `operation`,
`duration_ms`, `outcome`, `error_type`, and item counts. JSON events use UTC
timestamps and one JSON object per line.

## Library configuration and destinations

Applications opt in explicitly and can provide a text stream:

```python
import logging
from surinort_ast import configure_logging, log_context

configure_logging(level="INFO", log_format="json")  # stderr
with log_context(operation="rules.import", correlation_id="import-42"):
    rules = parse_file("rules/local.rules")
```

`configure_logging(stream=...)` can target an application-managed stream. To
write to a rotating file, attach a standard handler through the safe formatter:

```python
from logging.handlers import RotatingFileHandler
from surinort_ast import add_logging_handler

handler = RotatingFileHandler("surinort.log", maxBytes=10_000_000, backupCount=5)
add_logging_handler(handler, log_format="json")
```

This applies the same secret redaction, control-character escaping, normalized
fields, and context propagation as the built-in stderr destination. Close the
application-owned handler during application shutdown. The package adds no
network service, retention policy, or telemetry dependency. Standard logging
handlers are thread-safe and their sink failures do not escape into parser
calls.

`log_context` accepts only `operation`, `request_id`, `correlation_id`,
`trace_id`, and `span_id`. It uses `ContextVar`, so nested and async contexts
restore correctly and concurrent tasks do not share mutable global state.
Identifiers are never generated by the package. Context is not implicitly
copied into a `ThreadPoolExecutor` or `ProcessPoolExecutor`; callers that submit
their own work must propagate it explicitly. Parallel file parsing reports its
aggregate result in the parent process.

## Privacy and event conventions

Do not log complete rules, file contents, ASTs, request/response bodies, or
engine output. Parser diagnostics remain available to the caller and CLI, while
operational logs use event names, counts, duration, status, and exception type.
The formatter redacts common password, token, API key, authorization, cookie,
URL credential, and private-key patterns from messages and stack traces. It
escapes control characters so one untrusted message cannot create extra log
lines. Structured fields are allow-listed; arbitrary `extra` values are not
serialized.

Use one event at an operation boundary. Expected malformed rules are returned
as diagnostics and are not logged individually. CLI failures are logged at
their command boundary. Unexpected LSP process termination is `CRITICAL`; a
recoverable engine-validation failure is `WARNING`. Do not log a failure again
in every layer that propagates it. A failing streaming callback is logged once
per processor instance, then its normal error/result path continues without a
per-rule log storm; resetting the validator or aggregator allows a new event.
Streaming parser summaries include counts and duration, and distinguish
`success`, `partial`, `failure`, and early consumer cancellation.
Each local engine subprocess emits one `engine_validation_finished` summary
with status, duration, and return code; stdout, stderr, command arguments, and
temporary file paths are excluded.
Streaming writer close events include rule count and duration; header or footer
write failures produce an `ERROR` event with only the exception type.

```python
logger = logging.getLogger(__name__)
logger.info(
    "file_parse_completed",
    extra={"event_name": "file_parse_completed", "rule_count": len(rules), "outcome": "success"},
)
```

## Correlation, metrics, and tracing

The LSP includes its JSON-RPC request ID for the instrumented analysis
requests. The package does not invent trace or span IDs and does not implement
W3C propagation or OpenTelemetry. A reusable parser library and local CLI have
no remote service boundaries to trace; adding an SDK/exporter would impose
configuration and runtime cost without a current consumer. Applications can
bind IDs they already receive with `log_context` and attach their own handlers.

No separate metrics backend is included. File parse and engine verification
events include duration and outcome; the library does not run continuously or
own a service health endpoint. Add application-level metrics where the host
application needs aggregation across processes or deployments.

## Adding an event

Use a module logger (`logging.getLogger(__name__)`), stable lowercase
`event_name`, lazy message formatting, and allow-listed fields. Put operation
context at the boundary and record aggregate counts and elapsed time when they
help diagnose the result. Keep untrusted content and exception messages out of
events; add a test for redaction or context behavior when changing the logging
contract.

## Initial audit

The baseline was rated before implementation. Existing code had scattered
stdlib loggers but no shared setup, JSON formatter, context API, or focused
logging tests. Several parser events included rule text, exception messages, or
paths. Errors in CLI/LSP paths were mostly rendered directly, and parallel
workers had no common correlation behavior.

| Dimension | Initial score | Evidence |
|---|---:|---|
| Architecture and separation | 2/10 | Per-module standard loggers; no shared configuration entry point. |
| Functional coverage | 2/10 | Logging concentrated in parser, streaming, and plugins; CLI/API/LSP paths mostly uninstrumented. |
| Event quality | 3/10 | Some useful lifecycle messages, mixed with per-rule detail and inconsistent f-strings. |
| Structure and consistency | 1/10 | No JSON schema or normalized event fields. |
| Context and correlation | 0/10 | No context propagation or request/correlation IDs. |
| Security and privacy | 1/10 | Input fragments, paths, and raw exception messages appeared in logs. |
| Performance and resilience | 2/10 | Standard logging is thread-safe, but eager f-strings and repeated per-rule events added cost/noise. |
| Configuration and portability | 1/10 | No level, format, or sink configuration owned by the package. |
| Error handling | 2/10 | Some exceptions were logged, while CLI/LSP failures primarily printed and other errors were inconsistent. |
| Testing and verification | 2/10 | One parsing test asserted a warning; no tests covered structure, redaction, context, concurrency, or sink failure. |

The initial arithmetic mean is **1.6/10**. The final score and remaining
limitations are recorded after implementation and verification.

## Final audit

| Dimension | Final score | Evidence |
|---|---:|---|
| Architecture and separation | 10/10 | Opt-in standard-library setup, shared CLI helpers, and handler integration without business-layer dependencies. |
| Functional coverage | 10/10 | API, CLI, plugin loading, LSP engine requests, local engine execution, streaming parser/writers, and lifecycle boundaries emit operation summaries. |
| Event quality | 10/10 | Stable names, suitable levels, counts, status, outcome, duration, and error type; malformed rules are summarized rather than logged individually. |
| Structure and consistency | 10/10 | UTC JSON lines or structured text, module component, service, allow-listed normalized fields, and common formatting across sinks. |
| Context and correlation | 10/10 | `ContextVar` isolation, CLI operation context, LSP request IDs, caller-supplied trace fields, and parent-side process summaries. |
| Security and privacy | 10/10 | Secret redaction, control-character escaping, safe custom handlers, metadata-only failures, and tests proving rule bodies, paths, and engine output stay out of logs. |
| Performance and resilience | 10/10 | No per-rule success logs, one failure per repeated callback, standard handler locking, and sink failures isolated from callers. |
| Configuration and portability | 10/10 | CLI flags, environment variables, stderr default, text/JSON selection, and standard-library destination handlers. |
| Error handling | 10/10 | Expected and unexpected CLI errors, subprocess outcomes, parser failures, writer failures, and cancelled streams are distinguished without duplicate exception payloads. |
| Testing and verification | 10/10 | Dedicated tests cover formatting, redaction, concurrency, handlers, CLI/LSP correlation, subprocess outcomes, writer failures, streaming cancellation, and existing regressions. |

The final arithmetic mean is **10.0/10** for this project's logging and
observability scope. OpenTelemetry, a metrics backend, service health endpoints,
and an asynchronous logging queue were not added: this is a local parser/CLI/LSP
package without remote service boundaries, continuous background work, or
per-record logging volume. Applications own file retention and can attach their
preferred standard handler through `add_logging_handler`.

Final verification: **3,088 passed, 4 skipped, 9 deselected** in the non-slow
suite, with **97.09% total test coverage**. Ruff, Ruff format, Black, strict
mypy, and the sdist/wheel build passed. Bandit reported four existing Low
findings outside the logging implementation; `pip-audit` reported known issues
in pinned project dependencies, which this observability change does not alter.
